# 关于Prompt的一些想法

Prompt一直是用好ai的关键，之前总是处于比较初级的用法，比如把需求描述清楚，给定角色等等，网上各种关于提示词的教程也错综复杂，所以一直没有去看，包括也有刷到过Prompt工程师等等，还有思维链等操作，当时觉得于自己而言作用并不大，自己可能也不需要那么复杂的prompt。

但是最近做个人网站项目，包括这大半年的AI使用来说，就是各家AI都会存在一定的问题也有自己的优势。GPT之前很久没用过，最近用它的codex还是比较ok的。但是有时候执行命令卡住（CodeX插件），在copilot里用的话就是上下文文本会消失，不知道是不是因为copilot的上下文长度限制。

用AI Studio里的Gemini 3.1 Pro 最大的问题就是额度限制，以及网页端的形式，对于稍微大一些的项目，很难形成很好的思路，但Gemini 3.1 Pro确实在一些方向性的指导上，能有比较好的作用。因此之前都在Gemini 3.1 Pro描述需求，先把框架搭起来，写个简单的md文件，有时候也会生成初版代码。然后再用Antigravity去细化，它是有一个plan模式，写好to do task，然后给出很完整的Implementation Plan.md文件，通过它可以把比较简单的prompt，然后扩成完整技术路线。如果Antigravity能一次生成的话也会用它，里面的Claude确实是比较好用，从项目实施的完整性来说，我觉得要优于Gemini 3.1 Pro。但最大的问题是Antigravity总是会断线，项目一大，需求一多它就容易歇菜。

所以最后的实施过程往往是会落到Vscode里的copilot插件，因为学生认证后有Pro会员，额度也比较多，原本能调用Claude、GPT、Gemini，但现在多了一些限制，最新版的模型基本上不能用了。之前主要是利用copilot去做补全，或者类似百科全书查询一样，多使用Ask功能，现在多用Agent的功能了，直接让它去编辑、生成代码，以及Debug。有时候需要加功能还是会去Gemini问一问，让它提供指导

最近使用Agent发现的几个痛点：

1. 版本管理，虽然现在都有版本回退功能，但好像不是很彻底。这个问题是可以通过Git去解决的，只是可能每次更改都提交一下
2. 长时记忆问题，我觉得在网页端效果还好点，但Agent端经常会忘记曾经改动的，对话一多记忆就消失了，并且进行更改时往往不会结合前面的更改，就是不连贯，也不会去做架构上的更新与改动，采用的方式通常是打补丁。这个问题经过最近的摸索是可以通过引入一些架构文档来解决的
3. 简单问题复杂化，Agent有时候在技术路线不明晰，没有足够约束的情况下，会将一些简单问题处理的很复杂，就容易添加很多行代码，会逐渐成长为屎山代码，重构越来越麻烦，也很难review。

最近Claude源码泄露，我就发现其实里面有很多关于Prompt的东西，为Agent提供了行为指导，这些都是提前注入式的，包括前阵子爆火的小龙虾，里面也有很多的Prompt，又阅读了一些推文，结合最近自己所遇到的问题，加上又正在做个人网站的项目，就做了一些尝试。

首先是让AI阅读整个项目代码，然后给出一个架构文档。当时这样做还是因为觉得整个项目非常大，每次都让ai阅读全项目会非常消耗token，就想为什么不能像人做笔记一样，阅读完就把架构给定好。既然定好了架构，那就让ai每次更新都要更新架构文档，并且写日志，这个想法很自然的就衍生了出来。并且因为ai经常只是打补丁，我经常会需要进行重构，所以就想关于这种行为约束也是可以直接写入相关文档，少打补丁多考虑架构层面的更新。补丁补到一定程度就是牵一发动全身，所以不如一开始就在架构层面进行更新。然后就是我要形成Blog模板，这种也是可以通过ai生成的，就想到Prompt我可不可以也有类似的模板，可以用来定义 AI Agent的全局行为规则。比如我需要加功能的时候，就在相关模板里描述某一次具体任务的需求，然后给定范围、约束、验收标准、输出要求等，这主要是功能上的更新。此外后面还借助Github workflow形成一套完整的**Copilot Repository Instructions**，规定了仓库的操作范式

现在进行整理就是，当做一个项目的时候可以有一套通用Prompt，让ai写好架构文档，把架构什么的都描述清楚，并且定义记录日志的行为，通过这个Prompt定义好初始行为和规范，并且加入一些约束，比如每次更新需要对文档进行相应更新，更新完后通过Git做好版本管理，这就相当于有个操作手册。

然后关于架构审查、定义新功能、Review等等都可以有对应的子Prompt，然后这些子Prompt可以形成一个完整的工作流。这样ai在更新代码过程中，不光会更新架构，还会记录更新，写日志，结构验证等等，这样AI每次动作都有迹可循，能够更好的进行Vibe code，虽然读取文档感觉多了，但token消耗会少不少，AI能更有针对性的找代码进行操作，代码更新也更有效率，bug会少很多，并且减少重复工作等。我在个人网站的实践中，也很明显的体会到了这一点，加入架构文档后真的基本上没出过Bug，最多只是修复无效。就像一个编程交流群里说的“只要需求提示输入得当，CLAUDE.md文档规范设置好，代码方面ai的理解和实现已经遥遥领先了”

现在架构非常重要，这个是需要自己去补足的。AI 可以帮你写代码，但目前它还设计不好系统架构。

架构是高内聚、松耦合的系统性思考，需要经验、判断力和全局视野。一个架构混乱的项目，AI 越帮越忙；一个架构清晰的项目，AI 如虎添翼。未来核心工程师的价值，正在从“实现功能”转向“设计出让 AI 能高效工作的系统”。系统设计、模块化、可扩展性这些“硬功夫”，在 AI 时代不但没贬值，截止到今天来看，还是看起来更值钱的。

然后可以有一些规范性Prompt文档，比如扫描目录是干什么的，什么函数是怎么用的。现在能够梳理好架构比写代码更重要（不借助ai的情况下或说不完全依赖）。并且现在AI写测试用例和测试程序非常好用

目前这种想法我觉得应该是很多大厂已经采用了，我只是最近才突然悟到，但我觉得这个悟的过程很重要，因此在这里记录自己的一些心得体会。目前这个Prompt还是处于初阶的应用，我觉得未来还可以针对具体的项目，去根据它的工具链、框架等去制定更合适的Prompt，比如面向机器人开发的，面向嵌入式的，但这些的实际效果我觉得还是需要继续探索，并且得去验证的。包括现在只是针对一个现有项目，如果说想针对一个新idea，从0开发呢，Prompt又要怎么写？Prompt我觉得也要与时俱进，及时更新，多关注相关公司的动态和GitHub仓库。没有最好的Prompt，只有最适合的Prompt。

此外我还觉得可以针对一些经验性的或者其他东西，形成文档，逐渐形成自己的知识库，在自己的专业领域加上这些提示或idea，可能会迸发出全新的灵感（阅读LLM Wiki推文后，我在考虑本地LLM能不能支撑起Wiki的搭建？如果可以的话，我觉得后面有必要尝试一下）

在后面的日子里，真的是要多记录，记录到md文件里，将知识内化，以后这些文档可能真会发挥意想不到的作用。
